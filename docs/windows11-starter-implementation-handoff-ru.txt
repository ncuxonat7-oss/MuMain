Задание на минимальный Windows 11 starter
Статус: готово для передачи на локализованную реализацию после отдельного разрешения. Сейчас выполнена только LOW подготовка; код не написан и процессы не запускались.

1. Решение и границы
Владелец 10.10.2026 в 21:14:23 UTC подтвердил один Windows 11 ноутбук для клиента, OpenMU и PostgreSQL, только закрытое тестирование. Источник: сообщение Sentinel_b51a1a8f189c8191969f779b05f7d288, «Окей» в ответ на вопрос о размещении. Не переспрашивать топологию. Железо и установленные компоненты неизвестны. Старые поля manifest о невыбранном хосте исторические; это задание и обновлённый portable plan их заменяют. Другие pins/hashes manifest остаются входными данными.

Результат будущей реализации: два пользовательских входа StartMU и CollectReport плюс необходимые внутренние helpers. StartMU также предоставляет явную остановку. Без GUI-фреймворка, updater, сервиса Windows, автозапуска, remote hosting, нового CI harness и изменения архитектуры.

2. Точные входы готового комплекта
Все hashes берутся из windows11-launch-manifest.json, а не с произвольного зеркала. До распаковки сверять ZIP/tar SHA256; после — записанные DLL hashes и Data overlay hash.

• Клиент: run37813650810 / artifact11567737809, source8d18a2bbf29b4e3c91d3f9bb3b645f68aadc3fc5. В ZIP лежит MuMain-windows-native-x64-release-editor-off-no-data.tar.gz. Цель — полный каталог клиента с DLL/CRT, NativeAOT bridge и shaders; не только Main.exe.
• Data/fonts: MuMain-data-4b0ab29c58b27fc4.tar.gz из закреплённого release. Распаковать в корень клиента; применить существующий scripts/apply-client-overlay.py с patches/client-socket-metadata.json. При missing Python или несовпадении hashes остановиться, не писать альтернативный overlay.
• Сервер: run37959672391 / patched-openmu-runtime11630698202. Это содержимое Startup/bin/Release, без внешнего source checkout. Разместить его в выделенном серверном каталоге пакета. Не применять source patch к DLL, не пересобирать и не использовать unpatched cache.
• DB: предложенный исходный baseline run38005996341 / baseline-data-final11651520969, member gameplay-test-db.dump. Владелец ещё должен явно подтвердить эту DB перед restore. Run16/run17 остаются отдельными fixtures и не выбираются по свежести даты.

Предлагаемые относительные области пакета: client, server, database, evidence и служебное состояние. Это проект layout, не утверждение о существующих каталогах на ноутбуке. Абсолютный путь выбирается при setup.

3. Разделение setup и обычной сессии
Первый setup выполняется отдельно и явно: проверка входных архивов, безопасная распаковка, overlay, проверка зависимостей, новый изолированный PostgreSQL cluster, роли и восстановление выбранной DB. Initdb/roles/restore допустимы только здесь. Шаги записывать без секретов; незавершённый setup не повторять автоматически. Существующий cluster/DB не перезаписывать и не удалять.

Обычный StartMU:
• Preflight без изменений: проверить подтверждённое состояние setup, собственные каталоги, версии/бинарные identities, доступность зависимостей и отсутствие другого собственного запуска.
• Определить конфликты портов5432/44406/55902; проверить также локальный служебный endpoint18080, если его сохраняет runtime. Конфликт не исправлять сменой чужих настроек или убийством процесса.
• Запустить только собственный PostgreSQL, затем OpenMU; дождаться явной готовности с ограниченным ожиданием, затем открыть клиент. Существующий workflow проверяет connect44406; это не полная проверка работоспособности game endpoint55902.
• Подтвердить фактическую loopback-привязку всех слушателей перед клиентом. Отсутствие подтверждения — отказ запуска.
• Сохранить PID, время старта и путь каждого собственного процесса. Повторный StartMU показывает активную сессию, не дублирует стек.

Остановка: перепроверить PID/start time/path, штатно закрыть свой клиент и OpenMU, дождаться их завершения, затем штатно остановить свой PostgreSQL. Точный безопасный способ graceful shutdown OpenMU ещё не установлен: workflow применяет Stop-Process, что нельзя автоматически назвать штатным завершением сервера. При отказе показать проблему, не переходить молча к force-kill. Чужие процессы не трогать. При ошибке старта откатывать только запущенные текущей попыткой процессы; DB и прогресс сохранять.

5. CollectReport
Только ручное создание локального отчёта: время, версия пакета/артефактов, статус preflight/start/stop и отфильтрованные ошибки. Без dump, credentials, account hashes и персональных данных; screenshots только по отдельному согласию. Если фильтрация не гарантирована, не добавлять сырой лог. Никакой отправки или upload. Диагностика не превращается в новый тестовый framework.

6. Неизвестное, блокирующее безопасное выполнение
A. ПК: CPU architecture/RAM/GPU+driver/свободный диск; реальные зависимости и runtime support. Численных minimum requirements пока нет.
B. .NET/ASP.NET10 и PostgreSQL: ранее работали10.0.11 и17.11. Точные установочные файлы/наличие/runtime configuration должны быть проверены; установка только из официальных источников с необходимым разрешением. Наличие Python для существующего overlay тоже неизвестно.
C. Локальная аутентификация: CI использует trust и временные параметры. Решение владельца о топологии не разрешает перенос trust, использование/сохранение credentials или изменение security settings. Нужна отдельная безопасная схема setup.
D. OpenMU bind: -resolveIP:loopback и advertised loopback адрес не доказывают bind всех listener sockets на loopback. Точный механизм конфигурации в pinned runtime ещё не проверен; при его отсутствии пакет не запускать.
E. OpenMU shutdown: подтвердить поддерживаемое graceful завершение и последствия для сохранения состояния.
F. На ПК пока нет материализованных и проверенных архивов; identities metadata не заменяют byte verification. Базу и локальный каталог ещё явно выбрать.

Эти неизвестные не мешают написать fail-closed preflight и контракт состояний, но не позволяют обещать безопасный рабочий one-click starter уже сейчас.

7. Приёмка и бюджет
Оценка реализации: MEDIUM. Один локализованный wrapper-проход без binary rebuild и без нового CI. Сначала реализовать fail-closed preflight и управление собственными процессами; не обещать установку или runtime proof в рамках LOW подготовки. Перед Windows выполнением проверить условия A–F и получить требуемые разрешения.

Минимальные критерии: неизвестное/неполный setup/неверный hash/порт занят → понятный отказ без изменений DB; второй запуск не дублирует процессы; нормальный запуск не выполняет restore; stop затрагивает только собственную сессию; report не содержит секретов и не отправляется. Проверка на реальном ПК и любое runtime выполнение — отдельный согласованный этап.

Никаких команд, абсолютных путей установки, поддерживаемых shutdown flags или ресурсных минимумов здесь не придумано. Parent отдельно ведёт публикацию GitHub; этот файл локальный.
